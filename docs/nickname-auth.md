# 닉네임과 로그인 식별

`username`은 표시용 닉네임이며 중복을 허용한다. 사용자 참조와 권한은 기존 UUID `id`를 쓴다.

| 가입 방식 | 로그인에 쓰는 값 | provider_user_id |
| --- | --- | --- |
| 이메일 | email + password | NULL |
| Google·네이버 | auth_provider + provider_user_id | 공급자가 발급한 식별자 |

이메일은 기존 `users_email_lower_uq` 인덱스로 대소문자를 구분하지 않고 중복을 막는다.
이 정책은 소셜 계정에도 적용된다. 같은 이메일로 다른 가입 방식을 선택해도 자동으로
계정을 합치지 않는다. 이메일을 받지 못한 소셜 계정은 NULL을 허용한다.

`users_provider_uq`는 이미 복합 UNIQUE이므로 새 인덱스를 중복 생성하지 않는다.
0021 마이그레이션은 닉네임 UNIQUE를 제거하고 기존 이메일 계정의 공급자 식별자를
NULL로 바꾼다. 이메일 계정의 이메일 누락과 OAuth 계정의 공급자 식별자 누락은 CHECK로 막는다.
사용자 UUID와 비밀번호, 작품·팀·세션의 참조는 유지한다.

로그인 요청은 `{ "email": "writer@example.com", "password": "..." }`를 쓴다.
기존 클라이언트의 `login_id` 요청 필드는 이메일 별칭으로만 받는다. DB 컬럼은 추가하지 않는다.
`GET /users/check-username`도 호환을 위해 남기지만 중복 여부는 조회하지 않는다.

## 적용 순서

백엔드 이미지 준비 후 가입 요청을 잠시 막은 상태에서 0021을 적용하고 새 API를 띄운다.
기존 API는 가입 시 provider_user_id에 닉네임을 넣으므로 새 CHECK와 함께 계속 실행하면 안 된다.
프론트는 백엔드 적용 후 배포한다. 구 프론트는 이메일 필드 별칭과 호환 API로 동작한다.

중복 닉네임 가입 이후에는 0020으로 바로 되돌릴 수 없다. downgrade는 UNIQUE 생성에서
트랜잭션 전체를 중단하며 계정을 삭제하거나 닉네임을 임의로 바꾸지 않는다.
